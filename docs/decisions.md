# Decisions

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-11-07 | Slint `=1.18.1` instead of the plan's 1.17.x; workspace `rust-version = "1.92"` | 1.18.1 is the current stable patch (Sep 21); it requires Rust 1.92, above AGENTS.md's 1.85 floor. |
| 2026-11-07 | Software renderer by default; FemtoVG stays behind the `ui/femtovg` feature | Spike: FemtoVG costs ~43 MB more private working set for a modest CPU saving. Numbers in `measurements.md`. Confirm in M3 with the real UI. |
| 2026-11-07 | The librespot session logs in with Spotify's desktop client ID (`streaming` scope, redirect `127.0.0.1:8898/login`); Hush's own Client ID is used for the Web API only | A token from Hush's Client ID passes the access point, but clienttoken rejects Hush's ID (HTTP 400) and login5 rejects the stored credential it yields under the default client ID (`INVALID_CREDENTIALS`), so no track loads. The session login runs once; librespot then reuses its cached credentials. |
| 2026-11-07 | Session login reuses `auth`'s PKCE code instead of `librespot-oauth` | `librespot-oauth`'s async login blocks a tokio worker on a std `TcpListener` and builds its own `reqwest::Client`. |
| 2026-11-07 | `vergen` locked to 9.0.6 in `Cargo.lock` | `librespot-core` 0.8.0's build script fails with vergen 9.1 (incompatible `vergen-lib`). |
| 2026-11-07 | Volume uses librespot's `SoftMixer`; the player gets `NoOpVolume` and `EqSink` reads the mixer's `VolumeGetter`, instead of a custom `AtomicMixer` | `SoftMixer` already keeps the mapped volume in an atomic and Spirc drives it; a custom mixer would duplicate it. Volume still lands after the EQ. |
| 2026-11-07 | `EqSink` streams 44.1 kHz to cpal 0.18 and lets Windows resample, instead of a resampler crate | cpal 0.18 opens WASAPI shared-mode output with `AUTOCONVERTPCM` and `SRC_DEFAULT_QUALITY`, so the audio engine converts to the device rate (usually 48 kHz). cpal 0.16 did not, which would have needed `rubato`. |
| 2026-11-07 | The safety limiter is a static soft-knee curve (knee at −1 dBFS, `tanh` above it); normalisation keeps librespot's dynamic limiter | It only has to catch EQ boosts that pass full scale, so it needs no attack/release state and cannot pump. |
| 2026-11-07 | Dark title bar via winit's window theme (`with_theme(Dark)` in Slint's attributes hook) instead of calling `DwmSetWindowAttribute` | winit already applies the dark mode on Windows; no unsafe code or HWND lookup needed. |
| 2026-11-07 | Software renderer confirmed with the real M3 UI | 9–13 MB private working set and under 4% of one core with the progress bar animating; numbers in `measurements.md`. |
| 2026-11-07 | Design direction changed to art-led and immersive (icon rail, poster type, bottom control strip; no glows, no glass panels) | The owner's preference over the Apple Music–style and the translucent-glass versions. The software renderer has no blur or shadows and drops rounded corners on gradients, so the design relies on solid fills and, from M8, the art itself. |
| 2026-11-07 | The window background changes colour while minimized | After a restore, Slint's software renderer repaints only dirty regions into a buffer Windows has cleared, leaving stale or black areas while the progress bar animates. A background change marks the whole window dirty. |
| 2026-11-07 | Seek and volume commands update the view before librespot confirms them | The player's confirming event arrives tens of milliseconds later, long enough for the bar or slider to visibly jump back. |
| 2026-11-07 | The Web API sign-in runs before the Connect device starts, not alongside it | Both browser logins listen on `127.0.0.1:8898`. With a stored refresh token the sign-in is one token request, so the device starts a few hundred milliseconds later. |
| 2026-11-07 | The app reads `/me` (24 h TTL) at startup and logs the user's name | It is the gateway's only real caller until library sync, and it exercises tokens, the HTTP cache and the gateway end to end. A warm start costs 0 requests. |
| 2026-11-07 | A 401 calls `TokenProvider::refresh_rejected(token)`, which replaces `expire()` | Several requests rejected with the same token trigger one refresh between them, not one each. |
| 2026-11-07 | Only endpoints in the gateway's TTL table go into `http_cache`, keyed by full URL | It keeps the table to a fixed set of URLs. Library pages land in entity tables instead (M5). |
| 2026-11-07 | `QUOTA_EXCEEDED` is detected by searching the whole 429 body | Spotify does not document where `reason` sits in the error body. |
| 2026-11-07 | A quota 429 fails its request at once, and queued P2/P3 requests fail while the breaker is open | Callers fall back to cached data rather than wait up to an hour. P0/P1 resume after `Retry-After`. |
| 2026-11-07 | Retry jitter comes from a freshly keyed `std::hash::RandomState` instead of `rand` | Spreading retries needs no quality randomness; it saves a dependency. |
| 2026-11-08 | List ids in `list_item` are integers: -1 Liked Songs, -2 saved albums, -3 the playlists, a playlist's key for its tracks; `model::List` maps to them in `store` only | One membership table and one cursor table for every list, with no string keys repeated thousands of times. |
| 2026-11-08 | `list_item.pos` has a plain (not unique) index | Prepending shifts positions with one `UPDATE`, which a unique index would reject mid-statement. |
| 2026-11-08 | An empty list is read whole and written page by page; a stored one is read newest first until a known `(id, added_at)` and the new entries are prepended in one write | The first sync fills the list as pages land without holding it in RAM; later syncs stay one request per list. |
| 2026-11-08 | Playlist tracks are synced only for playlists the user owns or collaborates on; a 403 still records the snapshot | Spotify answers 403 for other playlists' items in dev mode. Recording the snapshot stops a daily retry that would cost a request each. Followed playlists load through librespot in M6. |
| 2026-11-08 | `KeyListModel` caches rows by entity key (300, oldest evicted) and marks them stale on `set_keys` instead of dropping them | Rows stay on screen while a sync reorders the list, then reload once; no blank flash on every synced page. |
| 2026-11-08 | Missing rows are requested at once, then at most every 100 ms while more go missing | A pure 100 ms debounce left the first screen of a newly opened list blank for 100 ms. |
| 2026-11-08 | The Controller runs its loop from launch; the Web API and the Connect device join it once started | The library page reads SQLite and must work during the browser sign-in, or when the device fails to start. |
| 2026-11-08 | Catalog lists use spclient's batched `extended-metadata` endpoint, up to 250 entities per POST | Spike: 12 tracks in 29 ms, an artist's 45 albums in 38 ms, 300 tracks in 59 ms, each in one request. An album page costs 2 spclient requests and an artist page 3, instead of one per track or album. The response does not keep the request order, so entities are matched by URI. |
| 2026-11-08 | `catalog` reads spclient's raw metadata protobufs and drops `librespot-metadata` | The parsed types keep only the IDs of an artist's albums and top tracks and parse many fields Hush never shows; the protobufs carry everything Hush needs. |
| 2026-11-08 | `CatalogSource` returns boxed futures | The service keeps its sources as `Box<dyn CatalogSource>` in fallback order; a trait with `async fn` cannot be a trait object. |
| 2026-11-08 | Album and artist lists share `list_item` and `sync_cursor`: an album's tracks under `2^32 + key`, an artist's top tracks under `2·2^32 + key` and its albums under `3·2^32 + key` | One membership table and one cursor table for every list. An album with a cursor is complete; an artist's cursor age drives the weekly refresh. |
| 2026-11-08 | Tracks and albums store their first credited artist's key; all artist names stay as display text | Enough to open the artist from a row or album header, with no credits table. |
| 2026-11-08 | Migration 0003 clears the stored library lists and cursors, so the next sync reads everything once | Rows synced before it have no artist key. For a 4,400-song library this is one first sync again (about 230 requests at P3). |
| 2026-11-08 | Followed playlists load through spclient when opened, and are kept until the daily playlist sync sees a new `snapshot_id` | Dev mode cannot read their items through the Web API. Opening an unchanged playlist costs nothing. |
| 2026-11-08 | The Web API fallback pages `/artists/{id}/albums` 10 at a time and has no artist top tracks | Dev mode answers `limit=50` there with HTTP 400; top tracks were removed from the Web API. |
| 2026-11-08 | `HUSH_CATALOG=web-api` in `.env` forces the Web API catalog | The plan's config switch; settings move to the database in M8. |
| 2026-11-08 | Play loads a context URI through `Spirc::load` (Liked Songs is `spotify:user:<username>:collection`), after `Spirc::activate` when Hush is not the active device | Spotify Connect then follows the album, playlist or artist for next and previous. Activity comes from librespot's session connected and disconnected events, so Hush calls `activate` only when needed. |
| 2026-11-08 | The Controller keeps the page history (at most 50 pages); rail pages clear it | One owner for navigation state; Back works across album and artist pages. |
| 2026-11-08 | Library search runs on every change of the search text; Spotify's catalog is searched once typing pauses for 300 ms, or at once on Enter | FTS5 answers in ~2 ms, so library matches can follow each keystroke at no cost. The pause is a cancellable sleep in the request's own task, so a newer query cancels the older one whether it is still waiting or already queued at the gateway. |
| 2026-11-08 | Search lists each kind once: up to 5 library matches, then Spotify's results without them | One list per kind keeps the page short; library matches lead without a second set of sections. |
| 2026-11-08 | Library search covers Liked Songs, saved albums, the user's playlists and the first artists of liked songs and saved albums | Entity tables also hold catalog entries from album, artist and search pages, which are not the user's library. |
| 2026-11-08 | FTS5 indexes are external-content tables over the entity tables, kept in step by insert and update triggers; the migration rebuilds them from existing rows | No second copy of the text, and no Rust code has to remember to update an index. Update triggers fire only when the indexed text changes, so a sync that re-reads unchanged songs does no index work. |
| 2026-11-08 | Library search filters with `+rowid IN (…)` | Without the `+`, SQLite drove the query from the 4,400 library keys, one index lookup each: ~100 ms per keystroke instead of ~2 ms. |
| 2026-11-08 | The search cache holds 64 KB of results (about 200 queries' first pages) instead of exactly 200 entries | It shares `kit::ByteLru`, which bounds memory in bytes, with the image cache. Entries older than 10 minutes count as misses. |
| 2026-11-08 | Search results are stored in the entity tables like any catalog entry, and the page lists their keys | Search rows load through the same `KeyListModel` path as every other list, and opening a result needs no further lookup to find it. |
| 2026-11-08 | Playing a song from search loads the listed songs as a track list (`LoadRequest::from_tracks`) | A search result has no album or playlist context; next and previous then follow the search results. |
